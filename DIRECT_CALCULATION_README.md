# N01 Smart Battery Calculator — direct annual calculation integration

## What changed

**New postcode-based route:** `POST /api/v1/calculations/generated-annual/`

The Next.js Step 1 collects an Australian postcode/state, exactly 24 hourly consumption readings in kWh, historical PV year, panel tilt and azimuth, and the user's optional data-retention choice. It saves only those inputs in the browser draft; no PV profile or annual CSV is generated by Next.js.

At Step 4, Next.js submits **one JSON request** to Django. Django:

1. Resolves an approximate location from the postcode and state.
2. Gets the selected historical year's hourly 5 kW PV output from Renewables.ninja (server-side token).
3. Normalises the PV data to 8,760 local-hour records (omitting Feb 29 for 2024).
4. Repeats the 24 hourly loads 365 times and inverse-scales PV for the immutable MATLAB source.
5. Creates the two-column `PV Generation,Load Data` CSV **internally** (never round-trips it through Next.js).
6. Sends the internally created file through the existing workbook parser/validation and GNU Octave execution method.
7. Responds with the normal calculation result (including warnings and legacy output CSV). If `retain_data=false`, it does not create calculation or stored-file DB records. If true, the existing PostgreSQL/storage retention path is reused.

Manual `.xls/.xlsx/.csv/.txt` upload **still works** through `POST /api/v1/calculations/client-workbook/` as before.

## Example JSON request

```json
{
  "postcode": "5000",
  "state": "SA",
  "suburb": "Adelaide",
  "year": 2024,
  "load_profile_24h": [0.4, 0.4, 0.4, 0.4, 0.4, 0.4, 0.8, 1.1, 0.7, 0.7, 0.6, 0.8, 0.8, 0.9, 0.7, 0.9, 1.0, 1.5, 1.8, 1.9, 1.4, 0.8, 0.7, 0.5],
  "tilt": 25,
  "azimuth": 0,
  "system_loss": 0.1,
  "battery_installed_cost_per_kwh": 1000,
  "retain_data": false
}
```

## Local setup (macOS)

Backend, in your Python virtual environment:

```bash
# .env should contain RENEWABLES_NINJA_API_TOKEN=<actual-secret-token>
python -m pip install -r requirements.txt
DJANGO_SETTINGS_MODULE=config.settings.development python manage.py migrate
DJANGO_SETTINGS_MODULE=config.settings.development python manage.py runserver
```

The `.m` files and the MATLAB optimisation constants are unchanged. GNU Octave must be installed for real calculations.

Frontend:

```bash
npm ci
# .env.local should contain NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000/api/v1
npm run typecheck
npm run dev
```

Open `http://localhost:3000/calculator/load-solar` and use **Postcode + 24-hour table**. The annual profile is generated when you click **Run Calculation** at Step 3 and proceed to Step 4, not when leaving Step 1.

## Verification

- Local parser checks: `python ../local_validation.py` from `backend` (or `python local_validation.py` from unpacked working directory).
- Full Django tests: `DJANGO_SETTINGS_MODULE=config.settings.test python manage.py test apps.calculations.tests_generated`
- Frontend type checks: `npm ci && npm run typecheck`
- API smoke test: `POST /api/v1/calculations/generated-annual/` using the JSON above. Requires an API token, postcode API access, Octave, Django and its dependencies.
- Deploy with Django `python manage.py migrate` and ensure production static-file collection: `python manage.py collectstatic --noinput`.

**Important limitations:** Real Renewables.ninja service availability/coverage, year-boundary handling, timezone/DST interpolation accuracy, backend storage permissions, Octave model execution and full production builds must be tested in your live environment. The default 2024 weather year is the latest previously verified available year, not a guarantee that newer data is unsupported. Postcode coordinates can be approximate. The load profile represents a repeated typical day, not a seasonal load forecast.
